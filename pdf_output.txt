Architecture and design
Problems found
Orchestration is hard‑wired and stage integration is “filesystem-coupled” instead of “artifact-
coupled.”
run_pipeline.py  imports each stage class directly and executes them via explicit  if N in  
etapas:  blocks (Pipeline orchestrator:  PipelineLicitaciones  in  run_pipeline.py , around
lines 20–200). As a result: - Adding a new stage requires editing the orchestrator (imports + control flow
+ summary printing). - Stages discover inputs by “latest file in a folder” globbing rather than receiving
explicit artifacts from previous stages (e.g., src/etapas/etapa3.py::_obtener_archivo_entrada
uses  FILTRADO_DIR.glob("Licitaciones_Filtradas_*.xlsx") ,  around  lines  87–95;  src/
etapas/etapa4.py::_obtener_archivo  
uses
ENRIQUECIDO_DIR.glob("Licitaciones_Enriquecidas_*.xlsx") , around lines 115–121).
This couples stages to naming conventions and directory structure, and increases the risk of mixing
artifacts across runs (especially if two executions overlap or an old file remains “latest”).
No explicit “Stage contract” (interface) and no shared pipeline context model.
Each stage returns a loosely-typed dict ( {'exito': True, 'stats': ...} ), but the keys differ
between stages (e.g., Stage 3 returns total_enriquecidas , Stage 2 returns total_filtradas ,
etc.). There is no typed context carrying run_id, input artifact paths, outputs, and metadata across all
stages.
Import-path manipulation instead of proper packaging.
Multiple modules inject paths via sys.path.append(...)  (e.g., src/etapas/etapa1.py  lines ~9–
13;  src/etapas/etapa2.py  lines ~7–12;  src/etapas/etapa3.py  lines ~14–18;  src/etapas/

and makes “install & run” much harder than it needs to be, especially for new developers.
Configuration is a mix of constants, Excel-driven config, and in-code assumptions.
src/utils/config.py  defines many defaults as class constants and also reads dynamic parameters
from PIVOT_MAESTRO.xlsx  ( Config.cargar_desde_pivot , around lines 135–182). Stages use a
mix  of  Config  as  a  class  vs  Config()  as  an  instance  (e.g.,  Etapa0Descarga  sets

self.config  =  Config  while  EnriquecedorAPI  uses  config  or  Config() ).  This
inconsistency increases mental overhead and complicates dependency injection/testing.
Side effects at import time.
src/utils/config.py  calls Config.validar_estructura()  at import (end of file, around lines
205–206). Import-time directory creation and warnings complicate unit tests and any tooling that
imports modules without intending to run the pipeline.
Impact
High. The current architecture makes the system harder to evolve safely, complicates reliable re-runs,
and increases the cost of adding or replacing pipeline stages.
Solution proposed
Introduce an explicit stage contract + a pipeline context + artifact passing (not folder-globbing).
A minimal, high-leverage refactor is to define: - A PipelineContext  (run metadata, config, artifact
registry).  -  A  Stage  protocol/ABC  with  name ,  run(context)  ->  context ,  and  optional
validate_inputs(context) .
Example (illustrative):
from dataclasses import dataclass, field
from pathlib import Path
from typing import Any, Dict, Protocol
@dataclass
class PipelineContext:
run_id: str
config: Any
artifacts: Dict[str, Path] = field(default_factory=dict)
metrics: Dict[str, Any] = field(default_factory=dict)
class Stage(Protocol):
name: str
def run(self, ctx: PipelineContext) -> PipelineContext: ...
Then  stages  produce  named  artifacts  ( ctx.artifacts["filtered_xlsx"]  =  path )  and
downstream stages consume those explicit keys (with a fallback mechanism if needed). This eliminates
accidental “wrong latest file” behavior and makes a stage replaceable without changing every other
stage.
Move toward a plugin-like registry for stages.
Instead of hard-coded imports + branching, define a stage registry:
STAGES = {

}
The orchestrator iterates through selected stage IDs, retrieving from registry. This makes “add a new
stage” mostly additive (new file/class + registry entry), not invasive.
Consider adopting a workflow orchestrator when/if operations mature.
If you expect growth in stages, schedules, retries, observability, and resuming from partial failures,
frameworks like Apache Airflow
 or Prefect
 are purpose-built for DAG execution, retries, state,
and resuming. Prefect explicitly supports task retries and caching/persisted results, which maps well to
“don’t repeat work” and “resume a failed step.” 
Priority of implementation
Short  term. Start  with  the  stage  contract  +  context  +  explicit  artifacts  (highest  ROI  refactor).
Orchestrator frameworks are a longer-term decision unless ops requirements justify them immediately.
Robustness and error handling
Problems found
Network resiliency is inconsistent and not centralized.
- Stage 0 ( src/etapas/etapa0.py ) uses requests.head  and requests.get  with timeouts and
limited exception handling, but no structured retries/backoff for transient failures (download execution
around lines 84–175).
- Stage 3 ( src/etapas/etapa3.py::_consultar_api ) has some retry behavior and special rules for
429/500 (around lines 136–181), but the retry strategy is embedded in the stage rather than shared/
reusable across HTTP calls. - Stage 4 calls two different external APIs (UTM + FX rate) and catches
exceptions, but one call embeds a credential (see security section) and both calls have no caching/
health  fallback  beyond  “log  warning,  keep  defaults.”  ( src/etapas/etapa4.py::_obtener_utm/
_obtener_usd , around lines 104–113)
No robust “resume from mid-pipeline” or checkpointing within long steps.
Stage 3 enrichment processes rows sequentially and only writes the final enriched output at the end
( _enriquecer_licitaciones  builds an in-memory list and then creates a DataFrame). If the process
fails at item 150/200, you lose all progress and must restart Stage 3. ( src/etapas/etapa3.py ,
enrichment loop around lines 110–134)
Input/output validation is partial and not uniform.
There is some validation (e.g.,  validar_archivo_excel  checks existence/sheets in  src/utils/
file_ops.py , around lines 19–60), but: - There is no standardized “DataFrame contract” between
stages (required columns, types, constraints). - Many operations rely on best-effort column matching
and silent fallbacks (e.g., Stage 4 returns 999 days when parsing fails; Stage 3 returns _api_error
fields). These are pragmatic, but the pipeline does not enforce sanity checks (e.g., “filtered count must
be > 0” or “enriched success rate must be above X%”) that would catch upstream schema drift early.

Error signaling is mixed between “return dict with exito” and “raise Exception.”
Some stages return {'exito': False, ...} ; others log and re-raise; the orchestrator sometimes
throws generic Exception("Etapa N fallo") . This reduces diagnosability and makes it harder to
implement consistent retry/resume policies.
Impact
High. Daily production automation touching external dependencies (web download + API + Excel IO)
will  encounter  transient  failures.  Without  central  retry  policies,  checkpointing,  and  sanity  checks,
reliability will degrade and manual intervention will increase.
Solution proposed
Centralize HTTP client behavior with retries, backoff, and timeouts.
Requests does not retry failed connections by default; you must configure retries explicitly (for example
using HTTPAdapter  + urllib3 Retry ). 
Example: a shared http.py  utility:
from requests import Session
from requests.adapters import HTTPAdapter
from urllib3.util.retry import Retry
def build_retrying_session() -> Session:
s = Session()
retries = Retry(
total=5,
connect=5,
read=5,
backoff_factor=0.5,
status_forcelist=[429, 500, 502, 503, 504],
allowed_methods={"HEAD", "GET"}
# keep idempotent by default
)
adapter = HTTPAdapter(max_retries=retries, pool_connections=20,
pool_maxsize=20)
s.mount("https://", adapter)
s.mount("http://", adapter)
return s
Then Stage 0/3/4 call through this shared session rather than embedding retry logic per stage. (This
also enables consistent logging and metrics around requests.)
For finer-grained retry policies (e.g., retry only on specific exceptions, add jitter, cap total retry duration),
consider a retry library like Tenacity wrappers such as stamina . 
Add checkpointing to Stage 3 enrichment and “resume mode” to the pipeline.
A practical pattern: - Maintain a durable cache or checkpoint file keyed by codigo  (e.g., SQLite, JSONL,
Parquet). - On start, load checkpoint, skip codes already enriched. - Append each successful (or failed)
API result to checkpoint immediately (or every N items). - At the end, materialize Excel.

Code quality
Problems found
Inefficient and duplicated text normalization in filtering.
src/utils/text_processing.py::contiene_palabras_clave  normalizes each keyword inside
the loop for every row check (around lines 196–201), even though Stage 2 already normalizes filter
values  when  loading  filters  ( src/etapas/etapa2.py::_cargar_filtros ,  lines  ~70–85).  This  is
classic hidden duplication that increases CPU time significantly as volume grows.
Row-wise DataFrame.apply  used multiple times for inclusion/exclusion/bypass.
Stage  2  filtering  is  implemented  as  Python-level  row  functions  ( df.apply(cumple,  axis=1) ),
repeated for inclusion, exclusion, and bypass ( src/etapas/etapa2.py , around lines 129–173). For
12k rows this might still be acceptable, but it won’t scale cleanly and is hard to optimize further without
refactoring.
Scripts contain repeated “main()” boilerplate and sys.path hacks.
Multiple stage files implement main()  and CLI execution patterns, each with custom prints and error
handling, in addition to the orchestrator. This increases maintenance surface, and changes to execution
behavior must be replicated across files.
Dependency declaration is incomplete.
requirements.txt  lists only  pandas ,  openpyxl ,  pytest ,  python-dateutil , but the code
imports  requests  and  pytz  (e.g.,  src/etapas/etapa0.py ,  src/etapas/etapa3.py ,  src/
etapas/etapa4.py ). This can break fresh installs and violates the “explicit dependencies” principle.
Type hints are partial and inconsistent.
Some components use typing, but many functions accept/return loosely typed dicts or DataFrames
without  typed  schemas.  Wider  use  of  type  hints  improves  refactoring  safety  and  enables  static
checking; this is the core motivation of Python’s type-hinting standard (PEP 484).

Solution proposed
Pre-normalize keywords once and compile matchers.
Replace  repeated  normalization  inside  contiene_palabras_clave  with:  -  keywords  normalized
once  at  load  time  -  a  compiled  regex  (or  Aho–Corasick  if  keyword  lists  grow  large)  -  vectorized
Series.str.contains
Example (simple and fast enough for many teams):
import re
def compile_keywords(words: list[str]) -> re.Pattern | None:
clean = [w.strip() for w in words if w and w.strip()]
if not clean:
return None
escaped = [re.escape(w) for w in clean]
return re.compile("|".join(escaped), re.IGNORECASE)
# usage:
# pattern = compile_keywords(filtros["incluir"]["nombre"])
# mask = df["Nombre Adquisición (norm)"].str.contains(pattern, na=False)
Refactor Stage 2 filtering to compute boolean masks instead of per-row apply.
Compute masks per column and combine ( |  /  & ) according to business logic. This yields large
speedups with the same semantics.
Introduce packaging and remove sys.path mutations.
Adopt  pyproject.toml  for project metadata and tool configuration; it is the standard modern
mechanism for Python packaging and tool settings. 
This also enables clean entrypoints like python -m licitaciones_pipeline run ... .
Add type hints where they reduce risk the most.
Prioritize: - Stage result objects (replace dicts with dataclasses / TypedDict / Pydantic models) - Config
model - API response parsing result model This aligns with PEP 484 goals (static analysis, refactoring
safety).

Solution proposed
Stage 3: introduce durable caching + controlled concurrency.
Durable cache often beats concurrency for “daily batch enrichment”: - Cache results by codigo  and
only call API for new/changed codes. - If concurrency is desired, use a semaphore + rate limiter so you
never exceed the portal’s constraints. A workflow framework can also manage retries and caching/

Stage 2: vectorize matching and reduce per-row Python execution.
Move  to  compiled  patterns  and  column-wise  masks.  This  typically  gives  order-of-magnitude
improvements in pandas-based pipelines.

Observability and operations
Problems found
Logging is present but not structured for production diagnostics and alerting.
ProjectLogger  writes to a timestamped file and stdout and prints a “RESUMEN DE EJECUCION” with
counts per log level ( src/utils/logger.py , around lines 125–156). This is helpful, but: - There’s no
stable run identifier propagated across stages (so correlating multi-stage logs is harder than necessary).
- Logs are plain text without structured fields (stage, run_id, artifact_path, record counts, API error
rates), limiting queryability in log platforms. - No log rotation policy; log directories may grow without
bound. Python’s logging cookbook documents RotatingFileHandler patterns. 
No business metrics are emitted automatically.
For a daily system, you want durable metrics like: - licitaciones downloaded - licitaciones filtered -
enrichment success rate - average API latency and error reasons - report generation time Prometheus
client libraries and instrumentation best practices are documented and straightforward to adopt. 
No automated anomaly alerts.
Examples that should trigger alerts: - Stage 2 filtered = 0 (likely schema drift or filter config issue) - API
success rate suddenly drops (portal issue, key expired, changed schema) - Report output missing
expected columns Right now, these conditions may only appear as warnings in a log file.
Logging approach is more “file-based application logging” than “event stream.”
For professional operations, treat logs as an event stream (stdout with aggregation), as described in the
Twelve-Factor principle on logs. 
Impact
High. Observability is what makes systems reliable at scale. Without metrics + alerting, operators learn
about failures only when analysts complain.
Solution proposed
Add a run_id and structured log context across all stages.
At pipeline start, generate run_id  and inject into all logs. Even without full JSON logging, prefix every
log line with run_id  + stage .
Introduce metrics instrumentation (lightweight).
A pragmatic approach: - Emit a compact  metrics.json  per run in  OUTPUT/LOGS . - Optionally
expose Prometheus metrics if you have a runtime that can scrape/push.
